# Windows and Linux automatic updates with three-asset releases

Status: Ready for implementation
Date: 2026-09-29
Source: Repository-owner brainstorm in the `feat-auto-update-windows-linux` workspace.

## Outcome and current state

Give Windows x64 and Linux x86_64 users a Sparkle-like path to discover, authenticate, install, and restart into a newer stable ChoscorDB version without losing workspace or database work. Keep Sparkle on macOS arm64. Starting with the next release, each GitHub Release must have exactly three attachments: one installable package for each platform.

At version 0.1.7, `desktop/app/updater_sparkle.mm` provides the macOS Updates menu and uses the existing `MainWindow::requestUpdateRestart` close path. `desktop/app/updater_disabled.cpp` is used elsewhere. The macOS app embeds `releases/latest/download/choscordb-appcast.xml`. The Windows/Linux workflow creates an unsigned portable ZIP and unsigned AppImage, then attaches both and a checksum file after macOS publication. The current latest `v0.1.7` Release has six attachments: a versioned DMG, duplicate `ChoscorDB.dmg`, appcast, Windows ZIP, Linux AppImage, and Windows/Linux checksum file. The public repository has no GitHub Pages site configured. See `cmake/MacOSUpdater.cmake`, `scripts/release/{macos,publish,attach_platforms,cross_platform}.py`, `.github/workflows/cross-platform-release.yml`, `docs/{MACOS_RELEASE,WINDOWS_LINUX_RELEASE}.md`, and `.claude/skills/release-new-version/SKILL.md`.

## Decisions and scope

1. Retain Sparkle and the signed, notarized versioned DMG on macOS. Move its stable appcast to GitHub Pages; its enclosure continues to reference the immutable versioned DMG Release URL.
2. Ship a **per-user Windows installer** instead of the portable ZIP. It must support installation and later upgrades without requiring administrator rights. Existing ZIP users install the new package once; do not silently move or delete their portable folder. Windows OS code signing is outside this work; clearly disclose that the installer is unsigned and may be warned about or blocked by Windows. A separate update signature does not confer SmartScreen reputation.
3. Keep the Linux AppImage. After a verified download, replace the AppImage at the path from which it was launched and restart from that path, provided the directory permits safe replacement. For a read-only location, symlink/ambiguous path, or other unsafe replacement condition, offer a manual download/install route and leave the original usable. Do not silently relocate it.
4. Use GitHub Pages for stable update metadata. Create a **dedicated Ed25519 Windows/Linux update key**, distinct from the Sparkle key. Embed its public key in production Windows/Linux apps. Publish signed metadata containing stable version, platform/architecture, immutable versioned Release asset URL, expected size and SHA-256 digest, and enough release information for an update prompt. Keep private keys outside the repository and shipped artifacts. Signing and publication must have a documented, reproducible maintainer workflow. Fail closed on bad signatures, hashes, version/architecture mismatches, insecure or unexpected URLs, and unsupported key identity. Never downgrade automatically.
5. Starting with the next release, attach exactly the versioned macOS DMG, Windows installer, and Linux AppImage. No duplicate `ChoscorDB.dmg`, appcast, checksum, manifest, SBOM, or other metadata attachment. Keep local build manifests, checksums, inventories, source and license archives, and bundled notices for verification and redistribution. GitHub's automatically generated source-code links are not Release attachments.
6. Build and verify all three packages against the same exact source tag before publication. Stage all three on a draft, verify remote bytes and tag/commit identity, then publish the complete Release. Advance Pages feeds only after all public package URLs and signatures/hashes are verified. A failed or partial operation is diagnosed and safely retryable; no updater should offer a missing package. Update the release skill and guides to this sequence.
7. Leave `v0.1.7` and older Releases intact. Existing macOS installs embed the old latest-Release appcast URL, which will stop working when a three-asset release becomes latest. Explicitly document a **one-time manual DMG reinstall** to enter the Pages feed. Existing Windows ZIP and Linux AppImage builds have no updater and likewise need a manual first install of the new version. Preserve application data and credentials during these installs.

Non-goals: changing the macOS updater framework, beta/prerelease channels, delta updates, Windows Authenticode signing, a Windows system-wide installer, automatic migration of old portable installs or old embedded feed URLs, and adding a fourth Release asset for compatibility. The exact installer technology and internal metadata serialization are implementation choices, subject to the observable requirements below.

## User flows and failure behavior

- On first normal production launch, Windows/Linux users are asked once whether to enable periodic background checks. Persist the choice and provide a way to change it. `Updates → Check for Updates…` remains available regardless of consent. Match the existing macOS menu's role, accessible naming, and general presentation. Do not start updater activity in tests, smoke tests, screenshots, or development builds.
- An available newer stable version shows its version and release information. Download and installation require an explicit user action. Show meaningful download/verification progress and allow cancellation before installation. A manual check reports “up to date” or a useful network/error state; background failures do not interrupt work.
- Before installation, use the existing `MainWindow` shutdown path. Pending edits, unsaved SQL, recovery, and active database work must retain their established prompts and persistence behavior. If the user cancels closing, leave the current app running and permit a later retry. Do not launch a replacement or installer until the app has safely closed its work.
- On Windows, a verified installer upgrades the per-user installation and restarts ChoscorDB only after success. On Linux, a verified AppImage replaces the launched file safely and restarts only after success. If download, verification, installer execution, replacement, or relaunch fails, report the failure without treating the update as installed; preserve a runnable previous version wherever the platform permits. Do not require privilege escalation.
- Never execute or install bytes solely because they came from GitHub or HTTPS. Reject tampered/stale/mismatched signed metadata and package bytes. Preserve the current app and offer retry or a manual route where appropriate. Avoid leaking private paths or secrets in user-facing errors or release metadata.

## Acceptance criteria and public test seams

| Criterion | Observable test seam |
| --- | --- |
| Windows and Linux production apps expose manual checks; isolated/dev runs do not start update traffic; consent governs periodic checks. | Launch packaged apps against a controllable HTTPS update endpoint and inspect menu, preferences, persisted consent, and endpoint requests. Native Qt tests cover menu identity and isolation. |
| A newer stable release is offered with correct version/notes; same, older, prerelease, wrong-platform, and malformed records are not installed. | Feed responses at the updater's public network boundary, observed through the packaged UI and captured requests. |
| Windows/Linux accept only metadata signed by the embedded dedicated public key and packages matching its size/hash and expected Release URL. | Serve valid and tampered metadata/packages from a local HTTPS fixture; observe offer, rejection, and absence of installer/replacement execution. |
| User approval, cancellation, and the existing close prompts protect active work; a canceled close leaves the app and data usable and permits retry. | Packaged/native UI with disposable SQLite workspaces, dirty editors, pending edits, and a controlled update fixture; inspect persisted data after restart or cancellation. |
| A per-user Windows install upgrades in place and relaunches the new version without admin rights; old ZIP installs have a documented manual transition. | Clean Windows user account: install version N, update to N+1 through UI, inspect version, installation path, profile/credentials, and Windows process exit/restart. |
| A writable Linux AppImage upgrades at its current path and relaunches; a read-only path gives a manual fallback without damaging the old image. | Clean Linux account: launch N from writable and read-only directories, update through UI, inspect path, version, executable bytes, and preserved app data. |
| A failed download, invalid signature/hash, canceled shutdown, failed installer/replacement, or unavailable Pages feed never leaves a falsely reported success or destroys the previous runnable app. | Controlled fault injection at HTTP/package and operating-system file/process boundaries, plus packaged end-to-end retry checks. |
| The macOS app still updates through Sparkle using the Pages appcast, while an old build's migration limit is documented accurately. | Signed update rehearsal with a Pages-like HTTPS feed and versioned DMG; inspect embedded URL and perform N → N+1 update. Review migration instructions against an existing 0.1.7 bundle. |
| A new Release has exactly three verified platform attachments from one tag; Pages feeds advance only after publication and public URL verification. | Release publisher dry run and fake GitHub/Pages adapters for draft, partial upload, conflict, retry, and feed failure; then inspect a real rehearsal Release and fetched Pages content before production rollout. |
| No private update key is present in source, app packages, Actions artifacts, Pages output, or release attachments. | Package/Pages inventories and release workflow validation; the publisher verifies signatures with the public key before publication. |

## Technical and operational constraints

- Reuse `desktop/app/updater.h` as the platform boundary and the current safe close behavior. Keep update/download/install work responsive and outside the Rust database engine. Follow the repository UI ownership rules in `AGENTS.md` and `desktop/design_system/AGENTS.md` if the design system changes. Preserve object names, focus, accessibility, and signals. Run the UI consistency and policy gates plus relevant native CTest targets.
- Preserve the current platform targets: macOS arm64 with minimum macOS 26.0, Windows x64, and Linux x86_64 AppImage built on Ubuntu 24.04. Do not claim older Linux compatibility without evidence. Version comparison uses the repository's stable `X.Y.Z` authority.
- Keep signed macOS production packaging and its exact-commit/tag verification. Adapt `scripts/release/macos.py`, `publish.py`, `attach_platforms.py`, `cross_platform.py`, their tests, the cross-platform workflow, release documentation, and the release skill together. Existing immutable/conflict checks must remain strict; no silent asset overwrite, tag move, or release rollback. Local metadata verification remains even though metadata is not attached to Releases.
- Enable GitHub Pages for the public repository and deploy stable HTTPS update metadata with a repeatable, access-controlled process. The repository currently reports `has_pages=false`. Prefer keeping the new private key on a maintainer-controlled machine rather than adding it to GitHub Actions; the implementation may choose a secure alternative only if it documents the trust and recovery model. Validate the actual Pages URL and public cache behavior before embedding it in production apps. For forks, bind feeds and asset URLs to the configured repository rather than silently using the production host.
- Document key creation, backup, rotation/recovery, Pages outage handling, partial-publication recovery, and the first manual migration. If a key is lost or compromised, existing clients must not silently trust an unverified replacement; manual reinstall is the safe fallback unless an authenticated rotation path is implemented.

Relevant platform references: [Sparkle feed and signed-update publishing](https://sparkle-project.org/documentation/publishing/), [GitHub Pages publishing sources](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site), [GitHub Release assets](https://docs.github.com/en/rest/releases/assets), and [Microsoft SmartScreen reputation](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation).

## Risks and deferred implementation choices

The three-attachment rule intentionally breaks the old macOS feed URL when a new Release becomes latest. The owner accepted manual migration; do not describe this as seamless updating for 0.1.7. Windows remains OS-unsigned, so SmartScreen or organization policy may interrupt or block installation even when the app's update signature is valid. GitHub Pages must be configured and verified before shipping a build that embeds its URL. The exact Windows installer technology, Pages deployment mechanism, signed metadata format, and check interval may be selected during implementation, provided they satisfy the behavior and tests above. If a platform cannot meet the safe replacement guarantees, surface the constraint before shipping automatic installation.
