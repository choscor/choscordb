# Result filtering, sorting, and duplicate row

Status: Confirmed for implementation  
Date: 2026-09-21  
Source: User brainstorm on SQL Results and Object Data, confirmed 2026-09-21

## Outcome and current state

Users can narrow and order the complete result in either SQL Results or Object Data, then page, copy, and export what they see. Users with a safely editable result can duplicate one row as a reviewed, staged insert.

Both screens use `QueryWorkspace` and `ResultTableModel`. `desktop/app/query_workspace.cpp` installs the table context menu; `desktop/app/object_data_workspace.cpp` constructs the Object Data grid; `desktop/app/main_window_ui.cpp` constructs the SQL Results grid. The current menu has three copy actions and, where available, Add, Delete, Restore, and Set NULL. Header context menus are suppressed; neither grid has filter or sort controls. `ResultTableModel` owns only the visible page and staged changes. The engine retains indexed pages of the original query and can revisit them without reexecuting SQL; see `docs/architecture/result-pipeline.md`. Page sizes are bounded (100–10,000), deferred values avoid loading large cells, and export currently replays the original result. Edit eligibility is checked against the source table; a query result may be read only. Applying grid edits already presents a SQL review, reports failure, and refreshes the result on success. The working tree was clean when this spec was written.

## Requirements and decisions

1. Add visible filter controls to both grids. A user adds one or more column conditions, joined with AND, and presses Apply. Controls support text contains/equals, numeric comparisons, type-safe true/false or date/time/binary equality where comparison is safe, and IS NULL / IS NOT NULL. Match and text sort without case sensitivity. Unsupported operators are absent for a column type; invalid values get inline validation and do not start a scan. Keep column headers visible in a zero-match state and offer Clear filters. No OR groups, regex, or free-text search in this scope.
2. Clicking a column header cycles ascending → descending → original order, with one active sort column. Show the active direction in the header. Sort typed values rather than their display strings, keep equal values in their original relative order, and place NULL last in both directions. Original order means the captured result order, including an SQL query's own ORDER BY. Do not rerun SQL to obtain it.
3. Filter and sort apply to the complete current result, not just the displayed page or already fetched pages. A control change may scan the remaining original result on demand. Show progress and Cancel; keep UI responsive and existing bounded memory/disk behavior. A cancelled or failed transformation leaves the previous controls, page, and view usable and shows its outcome. A column with deferred large values cannot be filtered or sorted; explain the unavailability. If this is discovered during scanning, fail the proposed transformation without changing the prior view. Do not silently compare truncated display text.
4. Transformations are scoped to one result. They remain active through paging, and clear on a new user SQL execution, next result set, or different object. Applying staged edits and refreshing the same result reapplies the accepted controls. Refresh failure preserves a usable prior view or reports its invalidation explicitly; never show stale data as current. The active filter and sort are visible. A change to either while edits are staged uses the existing Apply / Discard / Cancel resolution before starting; Cancel preserves the prior controls and staged rows.
5. Pager state, visible row numbering, Copy selected cells/rows, and Copy current page describe and use the transformed page. Export includes the *full* filtered result in displayed sort order, with its scope clear before starting. With no controls active, existing copy/export semantics hold. Export must not accidentally use only the visible page or an unfiltered backing result. The no-match view exports zero data rows under the existing format/header rules.
6. Add **Duplicate row** to the table right-click menu in both screens. The action targets the row under the pointer, even if another row was selected; it is unavailable for empty space or where insert eligibility cannot be verified. Show it disabled with the existing read-only reason for a noneditable SQL result. Duplicate exactly one row per activation. Create a staged insert, copy ordinary insertable values (including staged edits in the clicked row), omit generated and key columns so database defaults can apply, and keep the new row reviewable before Apply. Preserve NULL versus empty values and typed values. Do not copy deferred values as truncated text; if a row cannot be duplicated safely, disable the action or show a clear failure without a partial staged row. Existing Apply review, constraint errors, Discard, and transaction safeguards remain authoritative. A duplicate that violates a unique or other constraint fails through that existing review/apply path and leaves the user's staged work available.
7. The only new row-menu item requested is Duplicate row. Filter controls are visible outside the menu; sorting is by header click. No immediate database insert, multi-row duplication, saved filters, query rewrite, or changes to unrelated tables are in scope.

## User flows and failure behavior

- Open SQL Results or Object Data, add conditions, and Apply. Validate before starting. A successful scan resets to page 1 of the transformed view, displays active conditions and any sort direction, and lets the user traverse every match. Clear filters restores the full result and its current sort. A sort change also starts at page 1.
- Clicking the same header three times visits ascending, descending, then captured order. Clicking a different header starts that column at ascending. An active filter remains in place when sorting changes.
- While a scan runs, progress and Cancel are available. Prevent competing operations that would invalidate the same result; stale completion events cannot replace a newer query/object/view. Cancellation or scan failure restores the previous usable view and communicates the reason. Disconnect/release invalidates the view under existing lifecycle rules.
- On a matching row, right-click and Duplicate row. The inserted row appears as pending, and Apply presents the existing review. Generated/key values are omitted. A failure to stage due to budget, unsupported value, or source invalidation is explained and atomic. Right-clicking blank space cannot duplicate a selected but unclicked row.
- An empty filter result retains headers, an empty-state message, active controls, and Clear filters. Paging is disabled as appropriate. Copy actions have no rows to copy; export uses the empty transformed result.

## Technical constraints and likely affected areas

Likely areas include `desktop/app/query_workspace.*`, `query_workspace_events.cpp`, `object_data_workspace.*`, `main_window_ui.cpp`, `desktop/models/result_table_model.*`, the `EngineAdapter`/CXX bridge, Rust core result storage/actor/export paths, and focused `tests/desktop/` and `crates/core/tests/` fixtures. Choose an implementation that preserves the existing single-execution query identity, indexed disk pages, transfer leases, deferred handles, typed cells, cancellation, and global/per-result memory budgets. Whole-result transforms and transformed export may need new engine-facing operations or result indexes; a Qt-only sort of one visible page does not meet this spec. Avoid eagerly holding the whole result in the UI or reexecuting arbitrary SQL, especially a statement with side effects. Keep original result bytes/ordering available for clearing controls and for rollback after a failed transform.

Existing edit eligibility, reviewed SQL generation, concurrency and transaction checks, and change prompts are the integration boundary for Duplicate row. A new staged row must remain mapped to the correct source values despite filtering/sorting and page changes. Preserve copy/export/deferred-value safety and stale request protection. Keep Qt presentation in C++ and engine/driver storage logic in Rust. Follow `docs/CI.md` for affected-code gates; verify native interactions at the public seams above. No persistence migration or rollout flag is required because settings are transient and there is no saved-format change in the approved behavior. Preserve existing supported platform behavior and accessible keyboard operation.

## Risks and deferrals

Whole-result sort can require consuming a large still-active cursor. It may take time and disk space; show honest progress and retain bounded memory. Database-native ordering may be dialect-specific, so use one documented typed comparator for the captured result and stable tie handling. Large/deferred values and source rows with uncopyable fields require explicit unavailability rather than partial or truncated duplication. SQL result sets without a verified insert target remain read only. Driver-specific binary/date equality and collation details may be resolved during implementation as long as the observable type-safe behavior above holds. No user decision remains open.
