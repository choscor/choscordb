# Table and view context actions: Drop and Rename

Status: Ready for implementation

Date: 2026-09-28

Source: Brainstorm with the user in the table right-menu-actions workspace.

## Outcome and current state

People browsing database objects can drop or rename a table or view from its navigator context menu, review the exact SQL first, and see the workspace reflect a successful change. The current menu in `desktop/app/navigator_controller.cpp` offers Refresh, Copy qualified name, Show DDL, and Generate SQL, but no schema mutation actions. `desktop/app/main_window_navigator.cpp` connects navigator actions to the workspace; `desktop/app/main_window.cpp` owns object tabs; `desktop/models/navigator_model.cpp` owns metadata refresh. `QueryWorkspace` tracks connection driver and active work; `EngineAdapter` submits SQL asynchronously.

## Scope and decisions

- Add Drop and Rename for table and view navigator nodes on SQLite, PostgreSQL, and MySQL. Do not add these actions to schemas, indexes, sequences, functions, columns, or other nodes in this feature.
- Execute against the selected object's connection after a dialog showing the exact SQL to be submitted. Do not open a SQL draft as the action's result.
- Drop uses a destructive confirmation button and Cancel as default. Show the kind, qualified name, and SQL. No typed-name confirmation, `CASCADE`, or `IF EXISTS`; let the database reject dependencies or a missing object and show its error. Cancel submits nothing.
- Rename accepts only a new unqualified object name in the same schema/database. Pre-fill the current short name. Show a live, read-only preview of the exact SQL. Reject empty, unchanged, or invalid names before submission; quote valid names as identifiers for the selected driver, including embedded quote characters. A dot is part of a short identifier if the driver permits it, not a schema separator. Let the database report collisions and permission errors.
- SQLite view Rename is disabled with an explanatory reason because SQLite has no direct view rename statement. Drop remains available for SQLite views. PostgreSQL and MySQL view Rename remain available.
- On successful Drop, close tabs for the dropped object and refresh its navigator parent. On successful Rename, retarget all matching open object tabs, including their recovery identity and visible title, reload their metadata, and refresh the parent. Preserve unrelated tabs and unsaved SQL drafts.
- If there are pending table-grid edits or active database work on the selected connection/object, block Drop/Rename with a clear message and let the user retry later. Recheck connection, object identity, and busy state after modal input and before submission. Do not submit duplicate actions while one is in flight.
- On failure, keep the object and tabs unchanged, surface the database error, and allow retry. On success, show a concise success notice. A metadata refresh failure should remain visible and retryable rather than claiming the tree is current.

## User flows and edge cases

1. Right-click a table or view. The menu exposes Drop and Rename beside existing actions; these target the clicked node even if selection differs. Unsupported SQLite view Rename is visibly disabled with a reason.
2. Drop opens a shared confirmation dialog with the final SQL and a non-default destructive button. Cancel or closing it does nothing. Confirm submits one statement. A dependent object, missing privilege, deleted object, or disconnected session yields an error without local success changes.
3. Rename opens a shared modal dialog with a single short-name field and live SQL preview. Submission is unavailable for empty/unchanged input or SQL that cannot be safely constructed. Confirm submits one statement. The operation stays within the original schema/database.
4. While the operation runs, prevent a second submission. Only the matching completion event may trigger success UI changes. A late event after disconnect or tab changes must not alter another connection's UI.
5. On success, refresh the containing navigator group, including when the object was found through filtering or paging. Update or close every matching tab on the same connection/profile context, including a second data tab opened through row navigation. Keep recovery state consistent.

The SQL preview must be generated by the same validated statement builder used for execution. Use the navigator's trusted object identity and driver-specific identifier rules; do not concatenate untrusted display text into executable SQL. Handle quoted, dotted, Unicode, and reserved-word names. The exact statement form is an implementation choice subject to each driver's supported syntax and verified tests. No dependency cascade or cross-schema move is offered.

- No storage migration or feature flag is required. Updated tab identity must persist through the existing recovery format. Existing context actions keep their behavior.

## Risks and assumptions

- Database dependency behavior and DDL transaction semantics vary; the dialog previews only the submitted statement, and server errors remain authoritative. MySQL notes that privileges tied to an object's old name are not migrated on rename. Do not imply otherwise in the UI.
- The user chose to block active work rather than cancel or discard it. If the existing model cannot determine object-specific pending edits, a conservative connection-wide block is acceptable.
- A failed metadata reload after a confirmed database change must not be mistaken for a failed DDL operation; report both outcomes accurately and offer Refresh.
- No further product decisions are deferred.
