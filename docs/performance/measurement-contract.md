# Release measurement contract

PRD §15 remains the acceptance source. Measurements use a separate executable linked to the production desktop library, a Release build, an owned temporary metadata database and a real display. Instrumentation does not add controls to the shipping UI; `docs/design/shadcn-reference.md` defines the pinned visual reference; the approved gallery supplies the shared production components.

The harness reports first window paint and workspace readiness separately, memory after one second idle and after one SQLite connection settles, at least 200 individual editor key-to-viewport-paint samples with nearest-rank p95, and GUI event-dispatch durations. On macOS the §15 memory gate uses `task_vm_info.phys_footprint`, which represents the process footprint used by Apple's memory tooling; resident size remains a separate diagnostic so shared/rendering mappings stay visible. A missing footprint sample fails macOS acceptance rather than falling back silently. Nested event dispatch is reported separately or excluded explicitly. A recursive one-million-row SQLite source is paged through the real grid: validate contiguous first/last values of every page, one query submission, total rows, process memory samples and core/cache reservation peaks without retaining event payloads. Revisit an archived page to verify navigation after eviction.

Normal shutdown starts after all rows are exhausted, with no manual transaction or export. Record accepted close through window closure; an external launcher must also include process termination. Timers enforce failure deadlines, not measured timestamp resolution. Report platform, CPU, Qt, build mode, rendering backend, document size, sample count and observation boundaries.

Fresh-profile startup is not a cold-cache measurement. In-process first paint excludes process creation and loader time. Offscreen rendering cannot establish displayed input latency. Memory samples can miss transient peaks. These limitations remain explicit in reports; unavailable metrics remain unverified rather than zero or passing. Full acceptance requires repeat runs, cold-start procedure, PostgreSQL session measurements and supported-platform evidence.
